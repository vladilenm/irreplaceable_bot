# Latency-патч подбора участников

**Дата:** 2026-08-22  
**Область:** Telegram-обработчик `#запрос`, matcher, внешние вызовы и наблюдаемость

## 1. Цель

Пользователь должен сразу видеть, что запрос принят, а каждый потенциально долгий этап должен завершаться результатом или контролируемой ошибкой за ограниченное время. Итоговый ответ заменяет первоначальный Telegram placeholder, поэтому один запрос занимает одно сообщение бота.

Патч также должен:

- сохранять конкретный безопасный код сбойного этапа вместо общего `processing-failed`;
- логировать длительность embedding, PostgreSQL, reranking и Telegram без пользовательского содержимого;
- не запускать два почти одновременных одинаковых запроса одного пользователя;
- продолжать обрабатывать разные запросы одного пользователя через существующую общую очередь.

## 2. Пользовательский поток

После извлечения `#запрос` обработчик сначала резервирует исходный Telegram `message_id` в `member_requests`. Это сохраняет текущую идемпотентность при повторной доставке одного update.

Для непустого нового запроса обработчик синхронно захватывает процесс-local single-flight ключ из `authorId` и SHA-256 хэша нормализованного текста. Для сообщений без `authorId` дополнительная дедупликация не применяется: их по-прежнему защищает уникальный Telegram `message_id`.

Если такой ключ уже активен, matcher повторно не запускается. Второй запрос получает отдельный ответ `Такой запрос уже обрабатывается.`, а его запись завершается с безопасным кодом `duplicate-in-flight`. Другой текст даёт другой ключ и поступает в очередь независимо.

Для принятого запроса бот сразу отправляет reply на исходное сообщение:

```text
⏳ Ищу подходящих участников…
```

`message_id` этого placeholder передаётся задаче в очереди. По завершении бот вызывает `editMessageText` для того же сообщения и заменяет его одним из результатов:

- форматированными 3–5 совпадениями;
- сообщением об отсутствии надёжных совпадений;
- безопасным общим сообщением о временной недоступности.

Пустой `#запрос` не запускает matcher и получает существующую прямую подсказку `Опишите запрос после #запрос.` без промежуточного placeholder.

Если очередь заполнена после отправки placeholder, placeholder редактируется сообщением о временной перегрузке, а запрос завершается кодом `queue-full`.

Single-flight ключ удерживается во время ожидания в очереди и выполнения pipeline. Он освобождается в `finally` при любом терминальном исходе, включая timeout, queue-full и Telegram-ошибку. Защита намеренно действует только внутри одного процесса и не координирует несколько реплик приложения.

## 3. Этапы matcher и таймауты

`MemberMatcher` явно разделяет три этапа:

1. `embedding` — получение query embedding;
2. `postgres` — exact top-20 через `MemberRepository.search`;
3. `reranking` — schema-validated LLM reranking и существующая evidence-проверка.

Query embedding ограничивается 15 секундами. Reranking ограничивается 60 секундами. Timeout охватывает весь вызов соответствующего этапа, а `AbortSignal` передаётся OpenAI-совместимому клиенту, чтобы по возможности отменить сетевой запрос, а не только перестать его ожидать.

PostgreSQL сохраняет существующий `statement_timeout=10s`; отдельный более длинный application timeout не добавляется. Ошибка или timeout одного этапа не позволяет запускать последующие этапы.

Операционные значения находятся в `runtime-defaults.ts`, а не добавляются в environment configuration:

- `embeddingTimeoutMs: 15_000`;
- `rerankingTimeoutMs: 60_000`.

## 4. Безопасные ошибки

Внутренний тип ошибки этапа содержит только разрешённые приложением `stage` и `code`, сохраняя исходную ошибку как `cause` для локальной классификации. Текст внешней ошибки, query, prompt, профиль и ответ модели не записываются в БД или структурированные логи.

Допустимые терминальные коды:

| Код | Значение |
|---|---|
| `duplicate-in-flight` | такой же запрос автора уже активен в текущем процессе |
| `queue-full` | ограниченная очередь заполнена |
| `embedding-timeout` | query embedding превысил 15 секунд |
| `embedding-failed` | embedding provider завершился ошибкой |
| `postgres-failed` | поиск shortlist в PostgreSQL завершился ошибкой |
| `reranking-timeout` | LLM reranking превысил 60 секунд |
| `reranking-failed` | LLM transport/schema pipeline завершился исключением |
| `telegram-ack-failed` | первоначальный placeholder не доставлен |
| `telegram-edit-failed` | успешный бизнес-результат не удалось записать в placeholder |

При ошибке embedding, PostgreSQL или reranking обработчик сначала пытается отредактировать placeholder безопасным сообщением о временной недоступности, затем сохраняет исходный код сбойного этапа. Если это аварийное редактирование тоже не удалось, первичный код этапа остаётся кодом запроса, а Telegram-сбой получает отдельный error log. Так первопричина не теряется.

Если matcher успешно вернул бизнес-результат, но итоговый edit не удался, запрос завершается с `telegram-edit-failed`. Общий код `processing-failed` удаляется из runtime-пути.

## 5. Наблюдаемость

Каждое выполнение этапа пишет одно структурированное событие завершения со следующими полями:

- `pipeline: member-request`;
- `stage: embedding | postgres | reranking | telegram`;
- `operation` для Telegram: `ack` или `edit`;
- `durationMs` как целое неотрицательное число;
- `outcome: ok | failed | timeout`;
- `chatId`, `threadId`, `messageId` на уровне Telegram orchestration;
- безопасные `errorClass`, HTTP status или стандартный system/SQLSTATE code, когда они доступны.

Лог embedding не содержит вектор или query. Лог PostgreSQL не содержит SQL и строки карточек. Лог reranking не содержит prompt, candidate profiles или model response. Telegram-лог не содержит текст отправляемого сообщения.

Таймер использует монотонный источник времени для длительностей. Существующие timestamps состояний продолжают использовать UTC ISO time.

## 6. Изменения компонентов

| Компонент | Изменение |
|---|---|
| `requests.ts` | immediate placeholder, edit вместо второго reply, in-memory single-flight, terminal error classification |
| `request.matcher.ts` | границы этапов, timeout/abort и duration logs |
| `embeddings.ts` | поддержка `AbortSignal` в query embedding call |
| `llm.ts` | поддержка `AbortSignal` для обеих веток structured completion |
| `telegram.ts` | редактирование Telegram-сообщения с теми же безопасными retry/logging правилами |
| `runtime-defaults.ts` | константы 15 и 60 секунд |
| `request.runtime.ts` | передача timeout-настроек matcher |
| `request.repository.ts` | сохранение конкретного terminal error code и placeholder id при доступности |

Схема PostgreSQL не меняется: `error_code` и `response_message_id` уже допускают нужные значения. In-memory single-flight не требует миграции.

## 7. Тестирование

Изменения выполняются по TDD. Новые тесты должны сначала воспроизвести отсутствующее поведение и упасть, затем пройти после минимальной реализации.

Проверяются:

1. Placeholder отправляется до запуска matcher, а результат редактирует тот же `message_id`.
2. No-match и matcher failure также редактируют placeholder, не создавая второй result reply.
3. Embedding timeout срабатывает на 15 секундах, сохраняет `embedding-timeout` и не вызывает PostgreSQL/LLM.
4. Reranking timeout срабатывает на 60 секундах и сохраняет `reranking-timeout`.
5. Ошибки embedding, PostgreSQL и reranking сохраняют соответствующие безопасные коды вместо `processing-failed`.
6. Успешный pipeline с неудачным final edit сохраняет `telegram-edit-failed`.
7. Два активных одинаковых запроса одного `authorId` вызывают matcher один раз.
8. Два разных запроса одного `authorId` оба поступают в очередь.
9. Single-flight ключ освобождается после успеха, ошибки, timeout и queue-full.
10. Duration log каждого этапа содержит stage/outcome/duration и не содержит пользовательского текста.
11. Повторная доставка того же Telegram `message_id` по-прежнему не создаёт нового ответа.

После focused-тестов выполняются полный `npm test`, `npm run typecheck` и `npm run build`.

## 8. Критерии готовности

Патч готов, когда валидный `#запрос` сразу получает placeholder, все терминальные результаты заменяют его через edit, embedding и LLM имеют проверенные timeout-границы, каждая ошибка сохраняет конкретный безопасный код этапа, а одинаковый активный запрос одного автора не запускает второй matcher. Разные тексты того же автора должны независимо обрабатываться существующей bounded queue.

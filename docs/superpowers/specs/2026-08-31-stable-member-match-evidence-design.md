# Стабильные дословные основания подбора участников

## Контекст

Production работает на commit `077a3d1`. Диагностика запроса про криптоблог
подтвердила, что `@maxresea` активен, имеет актуальный embedding и занимает первое
место exact vector search. При этом повторные `/test_request` иногда не показывают
его в финальном ответе.

После vector search текущий matcher просит LLM вернуть `memberId` и дословный
`evidence`. Код принимает результат только тогда, когда полученная строка является
точным, чувствительным к регистру и пробелам substring исходного `profileText`.
Такой контракт защищает факты, но делает валидность кандидата зависимой от точности
копирования текста моделью. Текущие безопасные логи не различают два случая:
модель не выбрала участника или выбрала его с недословным evidence. Новое решение
устраняет второй случай для всех нынешних и будущих карточек и добавляет безопасные
счётчики для различения оставшихся причин.

Отдельная production-проверка показала, что сейчас в
`club.member_matching_source` находятся только две строки; обе активны и
проиндексированы. Регины нет ни в source view, ни в web-проекции бота. Добавление
или исправление её исходной карточки не входит в эту задачу.

## Цель

Исключить случайное отбрасывание подходящего участника из-за того, что LLM неточно
скопировала основание из анкеты. Решение должно одинаково работать для любого
участника, добавленного через текущий каталог, и сохранять гарантию: пользователю
показывается только дословный, проверенный кодом фрагмент `profileText`.

## Не входит в задачу

- профильные исключения или хардкод `@maxresea`;
- импорт отсутствующих участников и изменение `club.member_matching_source`;
- изменение embedding model, размерности, content hash или PostgreSQL vector search;
- гарантирование полностью одинакового состава кандидатов при любом недетерминированном
  решении LLM;
- ослабление проверки фактов через fuzzy matching, нормализацию или публикацию
  модельного пересказа;
- изменение публичного порога три, приватного порога один или максимума пять;
- deploy, push или изменение production без отдельного явного разрешения.

## Рассмотренные подходы

### 1. Code-owned evidence options — выбран

Код детерминированно нарезает каждый `profileText` на дословные фрагменты, выдаёт
им локальные ID и передаёт модели пары `evidenceId + text`. LLM возвращает только
`memberId + evidenceId`. В Telegram код подставляет исходный текст по ID.

Преимущества: модель больше не копирует отображаемый текст; строгая достоверность
сохраняется; механизм не зависит от конкретных username или предметных областей.

### 2. Повтор текущего запроса

Повтор может случайно получить корректную цитату, но сохраняет исходную причину,
увеличивает задержку и стоимость каждого проблемного запроса. Не выбран как
основной механизм.

### 3. Отказ от LLM и публикация vector top-N

Даёт наиболее детерминированный состав, но превращает семантическую близость в
окончательное решение и повышает риск слабых совпадений. Не выбран без отдельного
eval-набора и изменения продуктового контракта.

## Архитектура

### Evidence options

`MemberMatcher` строит для каждого участника непустой массив evidence options:

```ts
interface EvidenceOption {
  evidenceId: string;
  text: string;
}
```

ID существует только внутри одного matcher-вызова и формируется из позиции
фрагмента (`e0`, `e1`, ...). Он не является идентификатором данных и не сохраняется
в базе.

Алгоритм нарезки работает с уже нормализованным `profileText`:

1. Пустые строки пропускаются.
2. Строка длиной до 300 символов становится одним option без изменений.
3. Более длинная строка сначала делится по границам предложений, сохраняя точные
   raw slices исходной строки.
4. Фрагмент длиннее 300 символов дополнительно делится по последнему пробелу в
   пределах лимита; если пробела нет, используется точный 300-символьный slice.
5. Пробелы по краям не публикуются; `trim()` допустим, потому что результат всё
   равно остаётся точным substring исходного `profileText`.
6. Пустые и повторяющиеся фрагменты удаляются с сохранением первого порядка.

Каждый option имеет длину от 1 до 300 символов и проходит финальную защитную
проверку `profileText.includes(option.text)` до передачи модели.

### LLM-контракт

Вместо полного `profileText` кандидат передаётся так:

```json
{
  "memberId": "web:…",
  "similarity": 0.4638,
  "evidenceOptions": [
    { "evidenceId": "e0", "text": "…" }
  ]
}
```

Ответ модели содержит максимум пять объектов:

```json
{
  "matches": [
    { "memberId": "web:…", "evidenceId": "e0" }
  ]
}
```

Prompt требует выбирать только переданные IDs, не добивать список слабыми
совпадениями и выбирать option, который самостоятельно объясняет соответствие
запросу. Имена, username и отображаемый текст по-прежнему принадлежат коду.

### Валидация и результат

Для каждого model match код:

1. находит `memberId` только в shortlist;
2. отклоняет повторный `memberId`;
3. находит `evidenceId` только среди options этого участника;
4. повторно подтверждает raw substring match option text в `profileText`;
5. возвращает `PublicMemberMatch.evidence` с exact option text;
6. сортирует принятые результаты по убыванию PostgreSQL similarity, затем по
   `memberId`, чтобы порядок не зависел от порядка объектов в LLM-ответе.

Formatter и его HTML-escaping не меняются.

## Один ограниченный повтор

Один повтор LLM разрешён только для структурно испорченного результата:

- JSON/Zod schema невалидна; или
- модель вернула непустой `matches`, но один или несколько объектов были отброшены
  из-за неизвестного `memberId`, дубликата или неподходящего `evidenceId`.

Пустой валидный `matches` означает осознанное отсутствие сильных совпадений и не
повторяется. Повтор использует те же query и evidence options плюс короткую
инструкцию выбирать только существующие IDs. Максимум — два LLM-вызова на один
matcher-запрос. Если второй ответ также невалиден, применяется обычный threshold:
приватный вызов возвращает результат только при наличии хотя бы одного принятого
кандидата, публичный — хотя бы трёх.

Частично валидный первый результат не публикуется до повтора, если в нём были
отброшенные model matches. После повтора используется только второй результат,
чтобы не смешивать два недетерминированных решения.

## Наблюдаемость и приватность

Matcher пишет одну безопасную итоговую запись без query, профилей, evidence, IDs,
username, embeddings или provider response. Допустимые поля:

```text
shortlistCount
modelMatchCount
acceptedCount
unknownMemberCount
duplicateMemberCount
unknownEvidenceCount
schemaValid
retryUsed
minimumMatches
outcome
```

`outcome` ограничен enum `completed | below-threshold | invalid-output`.
Эти счётчики позволят отличить слабый model selection от структурного/evidence
отбрасывания, не раскрывая персональные данные.

## Границы компонентов

### `src/member-evidence-options.ts`

Новый чистый модуль нарезает `profileText`, выдаёт options и гарантирует exact
substring/length invariants. Он не знает о Telegram, PostgreSQL или LLM.

### `prompts/member-matcher.md`

Описывает выбор `memberId + evidenceId` и запрещает создавать новые IDs.

### `src/request.matcher.ts`

Формирует options, строит новый schema, валидирует пары IDs, управляет одним
повтором, сортирует accepted matches и пишет безопасные счётчики.

### `src/llm.ts`

Транспорт не получает matcher-специфической логики. Существующее поле
`retryInstruction` используется вторым явным вызовом из matcher.

### `src/requests.ts` и `src/private-request-command.ts`

Интерфейс `PublicMemberMatch` и формат ответа сохраняются. Публичный и приватный
пути автоматически получают одинаковое поведение через общий `MemberMatcher`.

## Тестирование

### Нарезка evidence

- короткая canonical line возвращается без изменений;
- длинная строка делится на exact фрагменты длиной не более 300;
- каждый option является raw substring исходного `profileText`;
- пустые и дублирующиеся options не создаются;
- Unicode, числа, единицы и регистр не меняются.

### Matcher

- выбранный `memberId + evidenceId` возвращает code-owned username и exact text;
- модель физически не может подменить отображаемый текст через response schema;
- unknown member, duplicate member и unknown evidence ID отклоняются;
- структурно испорченный первый ответ вызывает ровно один повтор;
- валидный пустой ответ не повторяется;
- второй невалидный ответ не вызывает третьего запроса;
- результаты сортируются по similarity и `memberId`;
- приватный минимум один и публичный минимум три сохраняются;
- prompt injection внутри option text остаётся недоверенным содержимым;
- логи содержат только разрешённые счётчики.

Регрессионный кейс использует общий профиль крипто-эксперта, но не добавляет
production username в реализацию. Тест воспроизводит старый дефект: модель выбирает
релевантного участника, однако не обязана копировать его текст; после перехода на
evidence ID кандидат стабильно проходит проверку.

## Release gate

Перед любым release обязательны:

```bash
npm test
npm run typecheck
npm run build
git diff --check
```

После отдельного разрешения на deploy выполняются повторные `/test_request` для
одинакового криптозапроса и минимум два других репрезентативных запроса. Проверка
подтверждает одинаковую сохранность релевантных кандидатов, exact evidence и
отсутствие персональных данных в логах. Изменение source data, импорт карточек и
deploy остаются отдельными действиями с отдельной авторизацией.

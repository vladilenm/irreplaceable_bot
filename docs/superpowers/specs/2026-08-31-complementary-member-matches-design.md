# Взаимодополняющие кандидаты для составного запроса

## Контекст

Приватная команда `/test_request` по отдельному запросу про блог находит
`@vladilenm`, а по отдельному запросу про крипту — `@maxresea`. Составной запрос
про прокачку блога по крипте возвращает `no_match`.

PostgreSQL exact search передаёт reranker-у общий shortlist без минимального
порога similarity. Текущий prompt, однако, требует, чтобы evidence одного
участника самостоятельно и прямо объяснял соответствие всему запросу. Поэтому
два участника, каждый из которых надёжно закрывает свою часть составного запроса,
могут быть одновременно отклонены.

## Цель

Разрешить reranker-у выбирать взаимодополняющих участников, которые совместно
закрывают разные части одного запроса. Для каждого выбранного участника код
по-прежнему должен публиковать только дословный evidence-фрагмент его анкеты,
который прямо подтверждает именно его вклад.

Пример ожидаемого поведения:

- запрос: помощь с прокачкой блога по крипте;
- кандидат про блог подтверждает часть про развитие блога;
- кандидат про крипту подтверждает предметную часть;
- приватный результат может показать обоих как взаимодополняющих кандидатов.

## Не входит в задачу

- отдельный embedding и PostgreSQL search для каждой части запроса;
- изменение JSON schema ответа модели;
- сохранение или отображение выделенных моделью частей запроса;
- ослабление проверки `memberId`, `evidenceId` или exact substring;
- изменение максимума пять, публичного минимума три или приватного минимума один;
- профильные исключения и хардкод конкретных usernames;
- deploy, push или изменение production.

## Рассмотренные подходы

### 1. Уточнить reranker prompt — выбран

Prompt явно разрешает рассматривать составной запрос как несколько потребностей
и выбирать кандидатов, которые совместно их покрывают. Evidence каждого
кандидата обязан прямо объяснять покрываемую им часть. Модель не должна добавлять
человека, который не подтверждает ни одной части запроса.

Подход минимален: существующий shortlist, response schema, code-owned evidence и
валидация остаются прежними.

### 2. Добавить явные facets в response schema

Модель могла бы возвращать выделенные части запроса и связывать каждого
кандидата с facet ID. Это сделало бы декомпозицию наблюдаемой, но потребовало бы
новой schema, дополнительной валидации и решения, можно ли доверять самим facets.
Для текущего дефекта это избыточно.

### 3. Выполнять поиск отдельно по каждой части

Отдельные embeddings и vector search повышают шанс извлечь кандидатов для каждой
темы, но увеличивают количество внешних вызовов, задержку и сложность объединения
shortlist. Текущий дефект возникает после retrieval, поэтому такой подход не
соответствует минимальному объёму изменения.

## Изменение поведения

`prompts/member-matcher.md` получает два явных правила:

1. Составной запрос можно разложить на отдельные потребности и выбрать разных
   участников, которые надёжно закрывают их совместно.
2. Evidence участника должен самостоятельно и прямо подтверждать хотя бы одну
   релевантную часть запроса, а не обязательно весь запрос целиком.

Остальные ограничения prompt сохраняются: только переданные IDs, максимум пять,
никаких выдуманных фактов и никакого заполнения списка слабыми совпадениями.

`MemberMatcher` не меняет алгоритм. Он уже способен принять несколько валидных
пар `memberId + evidenceId`, отсортировать их по similarity и применить текущий
minimum. Валидный пустой ответ по-прежнему не повторяется; structurally invalid
ответ по-прежнему получает не более одного повтора.

## Тестирование

В `src/request.matcher.test.ts` добавляется регрессионный сценарий с двумя
обобщёнными профилями без production usernames:

- один профиль содержит дословное evidence про развитие блога;
- второй содержит дословное evidence про крипту;
- запрос объединяет обе потребности;
- модель выбирает оба существующих `memberId + evidenceId`;
- matcher возвращает обоих с code-owned usernames и exact evidence;
- переданный system prompt явно разрешает совместное покрытие разных частей
  составного запроса.

Тест сначала должен падать на текущем prompt, затем проходить после его
минимального изменения. После этого выполняется полный release gate:

```bash
npm test
npm run typecheck
npm run build
git diff --check
```

## Release и production

Изменение является локальным WIP до отдельного разрешения на deploy. После
авторизованного deploy smoke-проверка повторяет составной и оба одиночных запроса.
Ожидается, что составной приватный запрос показывает обоих взаимодополняющих
кандидатов, а одиночные запросы сохраняют прежнее точное поведение.

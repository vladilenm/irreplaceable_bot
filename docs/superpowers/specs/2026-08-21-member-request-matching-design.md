# Подбор участников по `#запрос`

Дата: 21 августа 2026 года
Статус: дизайн согласован в диалоге, ожидает ревью письменной спецификации

## 1. Цель

Добавить в Telegram-бот Клуба Незаменимых автоматический подбор участников. Когда пользователь публикует сообщение с точным хэштегом `#запрос` в любой теме целевой форум-группы, бот анализирует текст запроса, выбирает 3–5 наиболее релевантных участников из базы клуба и отвечает на исходное сообщение в той же теме.

Для каждого участника ответ содержит:

- Telegram username из карточки;
- одну короткую причину релевантности, основанную на тексте карточки.

Отдельное согласие на упоминание не требуется. Участник допускается к подбору, если его карточка заполнена и содержит корректный Telegram username.

Ожидаемый масштаб — до 1000 активных карточек.

## 2. Границы задачи

Входит в первую версию:

- точный trigger `#запрос`;
- получение карточек из Notion;
- локальная синхронизированная копия карточек в SQLite;
- embeddings через OpenAI;
- семантический shortlist из 20 карточек;
- LLM-переранжирование и формирование 3–5 объяснений;
- проверка результата кодом;
- reply на исходное Telegram-сообщение;
- защита от повторной обработки и ограничение параллелизма;
- автоматические тесты и эталонная оценка качества.

Не входит:

- редактирование карточек через бота;
- ручное подтверждение кандидатов;
- личные сообщения вместо публичного ответа;
- поиск по истории чата или контексту соседних сообщений;
- отдельная vector database;
- система отзывов на рекомендации;
- административный веб-интерфейс;
- несколько клубов или несколько целевых Telegram-групп.

## 3. Архитектурное решение

Проект сохраняет текущую модель: один Node.js-процесс, SQLite и вертикальные продуктовые срезы. Полная перестройка на глобальные controller/service/repository-слои не нужна.

Функция становится новым вертикальным срезом рядом с радаром и сводкой:

```text
Telegram #запрос
  -> детерминированный trigger и idempotency
  -> embedding запроса
  -> локальный semantic top-20
  -> LLM выбирает 0–5 кандидатов
  -> код валидирует результат
  -> reply с 3–5 участниками либо сообщение об отсутствии результата
```

Внешние системы скрываются за двумя портами:

```ts
interface MemberDirectoryProvider {
  listMembers(): Promise<MemberSourceRecord[]>;
}

interface EmbeddingProvider {
  embed(texts: readonly string[]): Promise<number[][]>;
}
```

Первая production-реализация `MemberDirectoryProvider` использует Notion. Первая реализация `EmbeddingProvider` использует OpenAI. Механизм поиска и Telegram-обработчик не зависят от конкретного источника карточек или embedding API.

### 3.1. Предлагаемые границы файлов

| Файл | Ответственность |
|---|---|
| `requests.ts` | Telegram-trigger, очередь, orchestration, idempotency и отправка reply |
| `request.matcher.ts` | embedding запроса, top-20, LLM-schema, проверка и итоговые matches |
| `members.ts` | доменные типы, `MemberDirectoryProvider`, синхронизация и активный индекс |
| `members.notion.ts` | чтение и пагинация Notion database |
| `members.repository.ts` | SQLite-запросы карточек, embeddings и состояния sync |
| `request.repository.ts` | SQLite-состояние обработанных запросов |
| `embeddings.ts` | `EmbeddingProvider` и OpenAI-адаптер |
| `prompts/member-matcher.md` | инструкции LLM-переранжирования |

Миграции и общий SQLite connection остаются в `database.ts`. Новые slice-specific запросы не добавляются в уже крупный `database.ts`, а используют экспортируемый `getDb()` через небольшие repositories. Существующие радар и сводка в рамках этой задачи не рефакторятся.

Зависимости передаются явно при регистрации обработчика и запуске синхронизации. Новый slice не использует service locator.

## 4. Карточка участника

### 4.1. Поля Notion

Первая версия читает одну Notion database со следующими свойствами:

| Свойство | Назначение |
|---|---|
| `Name` | отображаемое имя участника |
| `Telegram` | публичный username для упоминания |
| `Profile` | свободное описание опыта, компетенций и интересов |
| Notion `page.id` | стабильный внешний идентификатор |
| Notion `last_edited_time` | признак обновления источника |

Карточка считается заполненной и активной, если:

- страница не архивирована;
- `Name`, `Telegram` и `Profile` непустые после нормализации;
- `Telegram` имеет безопасный формат username.

`Telegram` нормализуется до значения без ведущего `@` и сравнивается без учёта регистра. Имя и описание проходят Unicode-нормализацию, удаление управляющих символов и схлопывание пробелов. В поисковый `profileText` попадают первые 2000 нормализованных символов; оставшийся текст не отправляется во внешние AI API в первой версии.

### 4.2. Локальная модель

Нормализованная запись содержит:

- `memberId` — стабильный внутренний ID, производный от источника и Notion page id;
- `source` и `externalId`;
- `displayName`;
- `telegramUsername`;
- `profileText`;
- `contentHash` канонического поискового текста `displayName + "\n" + profileText`;
- `sourceUpdatedAt`;
- `active`;
- номер успешного поколения синхронизации.

Embedding хранится отдельно:

- `memberId`;
- имя embedding-модели;
- размерность;
- `contentHash`, для которого рассчитан вектор;
- вектор в компактном `Float32` BLOB.

Описание и embedding не пишутся в логи.

## 5. Синхронизация Notion

Синхронизация запускается:

- при старте процесса;
- затем по `MEMBER_SYNC_CRON`, по умолчанию каждые 15 минут.

Одновременно может выполняться только одна синхронизация.

Алгоритм:

1. Получить все страницы Notion с пагинацией.
2. Нормализовать карточки и определить активные записи.
3. Сравнить `contentHash` и embedding-модель с локальным snapshot.
4. Пакетно запросить OpenAI embeddings только для новых и изменённых карточек.
5. После полного успешного fetch и embed одной SQLite-транзакцией:
   - upsert карточек и embeddings;
   - деактивировать карточки, отсутствующие в полном snapshot или ставшие неполными;
   - зафиксировать новое поколение и время успешной синхронизации.
6. Атомарно заменить индекс в памяти новым поколением.

Сетевые вызовы не выполняются внутри SQLite-транзакции.

Если Notion или OpenAI недоступны, новое поколение не фиксируется. Бот продолжает работать по последнему целостному snapshot. Если успешного snapshot ещё нет, запросы получают нейтральный ответ о временной недоступности.

Смена `EMBEDDING_MODEL` или размерности вектора инициирует полную переиндексацию всех активных карточек до активации нового поколения. Векторы разных моделей никогда не сравниваются.

## 6. OpenAI embeddings и локальный поиск

Embeddings используют отдельную конфигурацию:

- `EMBEDDING_API_KEY` — OpenAI API key;
- `EMBEDDING_MODEL` — обязательное имя embedding-модели;
- `MEMBER_SYNC_CRON` — расписание синхронизации;
- `NOTION_TOKEN` и `NOTION_DATA_SOURCE_ID` — read-only доступ к data source карточек через Notion API version `2026-03-11`.
- `REQUEST_MATCHING_ENABLED` — feature flag, по умолчанию выключен;
- `REQUEST_MATCH_CONCURRENCY` — параллелизм pipeline, по умолчанию `2`;
- `REQUEST_QUEUE_LIMIT` — предел ожидающих запросов, по умолчанию `50`;
- `REQUEST_PROCESSING_TIMEOUT_MINUTES` — timeout stale reservation, по умолчанию `10`.

Embedding-конфигурация отделена от `AI_API_KEY` и `AI_MODEL`: основной LLM-переранжировщик может оставаться Anthropic или OpenAI-compatible.

Для запроса бот:

1. удаляет trigger `#запрос` из текста;
2. проверяет, что после удаления остался содержательный запрос;
3. получает один embedding запроса через OpenAI;
4. вычисляет cosine similarity со всеми активными векторами текущего поколения;
5. исключает автора запроса по Telegram username, если он присутствует в базе;
6. передаёт LLM максимум 20 лучших карточек.

При 1000 участниках линейное сравнение в памяти достаточно быстро и не требует `pgvector`, Pinecone или SQLite vector extension.

## 7. Telegram-trigger и idempotency

Новый обработчик регистрируется до terminal capture middleware. Он получает текстовые сообщения и captions из `TARGET_CHAT_ID` во всех форум-темах, независимо от `TRACKED_THREAD_IDS` сводки.

Как и существующий capture, обработчик требует выключенного Telegram Privacy Mode и прав бота на чтение сообщений целевой группы. Текущий startup preflight продолжает проверять эти условия.

Trigger определяется по Telegram hashtag entity и нормализованному точному значению `#запрос`, без учёта регистра. Обычные сообщения завершаются до любых обращений к Notion, OpenAI, SQLite-поиску или основному LLM.

Обрабатываются:

- новые сообщения с trigger;
- отредактированные сообщения, впервые получившие trigger и ещё не имеющие записи обработки.

Редактирование уже обработанного запроса не создаёт новую рекомендацию. Пользователь может отправить новый запрос отдельным сообщением.

До внешних вызовов создаётся строка `member_requests` с уникальным ключом `(chat_id, tg_message_id)`. Состояния:

- `processing`;
- `completed`;
- `no_match`;
- `failed`.

Сохраняются thread id, author id, хэш запроса, времена обработки, количество matches и Telegram id ответа. Повторная доставка того же update не запускает pipeline повторно.

Запросы проходят через ограниченную очередь. Значения по умолчанию: не более двух одновременных pipeline и не более 50 ожидающих запросов. При заполненной очереди бот отвечает о временной перегрузке, не вызывая внешние API.

## 8. LLM-переранжирование

Основной LLM получает только shortlist, а не всю базу. Каждая карточка передаётся как недоверенные данные с явными границами.

Структурированный ответ:

```ts
interface MemberMatchOutput {
  matches: Array<{
    memberId: string;
    reason: string;
    evidence: string;
  }>;
}
```

Модель может вернуть от 0 до 5 matches. Для каждого кандидата:

- `memberId` должен принадлежать shortlist;
- ID не должен повторяться;
- `reason` — одна короткая причина, пригодная для публичного ответа;
- `evidence` — дословный фрагмент `profileText`, подтверждающий причину.

После schema validation `reason` ограничивается 160 символами, а `evidence` — 300 символами.

Код нормализует пробелы и регистр и проверяет, что `evidence` действительно является подстрокой исходной карточки. Кандидаты с неизвестным ID, повтором, отсутствующим evidence или нарушенными ограничениями удаляются.

Telegram username и имя никогда не генерируются LLM: они подставляются из локальной записи после проверки `memberId`.

Если после проверки осталось 3–5 кандидатов, они публикуются. Если осталось меньше трёх, бот не дополняет список слабыми совпадениями и отвечает, что надёжный подбор не найден.

## 9. Формат ответа

Бот отвечает на исходное сообщение в той же Telegram-теме:

```text
🔎 Могут подойти:

1. @anna_product — запускала B2B-продукты с нуля и проводила первые enterprise-продажи.
2. @mikhail_saas — отвечает за go-to-market SaaS и работу с корпоративными заказчиками.
3. @olga_sales — выстраивала пилоты и продажи первым крупным клиентам.
```

Форматирование, нумерация, escaping и mentions принадлежат коду. Причины ограничиваются по длине до отправки. Один запрос создаёт не более одного публичного ответа.

Если текст после `#запрос` пустой, бот просит описать запрос. Если нет трёх надёжных совпадений, бот сообщает об этом без упоминаний. При временном отказе embeddings или LLM бот сообщает о недоступности подбора и не публикует случайных кандидатов.

## 10. Ошибки и восстановление

- Notion sync и запрос embeddings повторяются один раз только для безопасных временных ошибок.
- Сбой синхронизации не повреждает активный snapshot.
- Сбой query embedding или reranking завершает конкретный запрос состоянием `failed` и не влияет на polling.
- Неизвестные ID и неподтверждённые evidence рассматриваются как недействительный LLM-результат, а не как участники.
- Ошибка Telegram send не переводит запрос в `completed`.
- При старте записи `processing`, старше `REQUEST_PROCESSING_TIMEOUT_MINUTES`, переводятся в `failed`; они не отправляются повторно автоматически, чтобы не создавать дубли. Пользователь может повторить запрос новым сообщением.
- В логах разрешены только IDs, счётчики, длительности, названия провайдеров и классы ошибок. Тексты запросов, карточек и публичные причины не логируются.

Из-за границы между Telegram send и фиксацией `response_message_id` абсолютная exactly-once доставка невозможна без поддержки Telegram. Дизайн минимизирует дубли persistent reservation до внешних вызовов и принимает крайне редкий риск повторного ответа при падении процесса сразу после успешной отправки, но до commit результата.

## 11. Безопасность и приватность

- `NOTION_TOKEN` получает доступ только к нужной базе и используется только сервером.
- Тексты карточек отправляются OpenAI при индексации.
- Текст запроса отправляется OpenAI для query embedding.
- Shortlist карточек и текст запроса отправляются настроенному основному LLM для переранжирования.
- Эти передачи являются осознанно согласованной частью дизайна.
- Управляющие символы удаляются, Telegram HTML экранируется, а username проходит отдельную проверку.
- Содержимое карточек считается недоверенным пользовательским вводом и не может менять system-инструкции или список допустимых IDs.

## 12. Наблюдаемость

Структурированные события без пользовательского текста:

- sync started/completed/failed;
- fetched, active, incomplete, changed и embedded member counts;
- активное поколение индекса и embedding model;
- request queued/started/completed/no-match/failed;
- размеры shortlist и final matches;
- latency query embedding, reranking и полного pipeline;
- очередь и её отказы;
- причины удаления недействительных LLM-кандидатов.

`/status` дополняется временем последней успешной синхронизации, активной embedding-моделью и числом активных карточек.

## 13. Тестирование

### 13.1. Автоматические тесты

1. **Trigger:** точный hashtag, регистр, captions, пустой запрос, другой чат, отсутствие hashtag, повторный update и edit после completion.
2. **Notion adapter:** пагинация, архивированные страницы, отсутствующие поля, небезопасный username и нормализация Unicode.
3. **Sync:** первоначальный snapshot, embeddings только для changed cards, model change full reindex, atomic rollback, deactivation missing cards и single-flight.
4. **Search:** cosine ordering, top-20, текущая generation, исключение автора и отсутствие inactive cards.
5. **Reranker:** schema validation, неизвестные и повторные IDs, выдуманное evidence, длинные reasons, 0–2 результата и валидные 3–5 результатов.
6. **Telegram:** reply на исходный message id в той же теме, безопасный escaping, один ответ на один запрос и отсутствие mentions в no-match/error ответах.
7. **Надёжность:** timeout и временные ошибки Notion/OpenAI/LLM/Telegram, заполненная очередь, сохранение старого snapshot и stale `processing` recovery.

Внешние сервисы в автоматических тестах заменяются fake providers и fake Telegram API. Реальные тексты карточек участников не коммитятся в репозиторий.

### 13.2. Эталонная оценка качества

Перед production-включением формируется защищённый набор из 20–30 репрезентативных клубных запросов и ожидаемых подходящих участников. Набор не должен содержать лишние персональные данные и не публикуется в открытом репозитории.

Критерий первой версии: минимум для 80% эталонных запросов хотя бы один ожидаемый участник присутствует в итоговых top-5 после полной валидации. Результаты также вручную проверяются на явно нерелевантные публичные упоминания.

Изменение prompt, embedding-модели или правил нормализации требует повторного прогона эталонного набора.

## 14. Критерии готовности

Функция готова к включению, когда одновременно выполнено следующее:

- Notion snapshot успешно синхронизируется и переживает временный отказ провайдера;
- до 1000 карточек индексируются без отдельной vector database;
- обычные сообщения не вызывают AI API;
- один валидный `#запрос` создаёт один reply в той же теме;
- публичный ответ содержит 3–5 уникальных usernames из активных карточек и grounded reason для каждого;
- неизвестный или выдуманный LLM-кандидат не может попасть в сообщение;
- при недостатке сильных совпадений нет искусственного заполнения списка;
- автоматические тесты, typecheck и build проходят;
- эталонная оценка достигает порога 80%;
- `REQUEST_MATCHING_ENABLED` включается только после первоначальной успешной синхронизации.

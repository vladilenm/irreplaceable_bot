# Дословные основания в результатах подбора

## Контекст

Production-проверка `/test_request` вернула корректного участника, но свободный
LLM-пересказ изменил смысл метрики: исходное «более 3,5 млн уникальных
пользователей» превратилось в «3,5 млн просмотров».

Источник и индекс содержат корректный текст. Ошибка возникает после reranking:
модель возвращает отдельные `reason` и `evidence`, код проверяет только
нормализованное наличие `evidence` в `profileText`, а пользователю показывает
непроверенный `reason`.

## Цель

Показывать в приватных и публичных результатах только дословный фрагмент анкеты,
который код подтвердил по исходному `profileText`. LLM может выбрать участника и
подходящий фрагмент, но не может сочинять или перефразировать отображаемое
основание.

## Не входит в задачу

- изменение данных `club.member_matching_source`;
- изменение embedding model, content hash или переиндексация карточек;
- изменение правил ранжирования PostgreSQL;
- изменение порогов: `/test_request` сохраняет минимум один результат, публичный
  `#запрос` — минимум три;
- повторный LLM-вызов для проверки ответа.

## Выбранный подход

LLM-ответ для каждого совпадения содержит только `memberId` и `evidence`.
`evidence` должен быть самодостаточным фрагментом длиной от 1 до 300 символов,
дословно скопированным из `profileText`. Поле свободного пересказа `reason`
удаляется из prompt и JSON schema.

После schema-валидации код:

1. находит `memberId` только в переданном shortlist;
2. отклоняет дубликаты;
3. принимает `evidence` только при точном raw substring match в соответствующем
   `profileText`;
4. передаёт в formatter именно проверенный `evidence`;
5. HTML-экранирует фрагмент перед отправкой в Telegram.

Нормализованное сравнение больше не считается достаточным для отображаемого
текста: даже безопасное изменение регистра или пробелов должно привести к
отбрасыванию результата, а не к публикации изменённой цитаты.

## Формат ответа

Формат списка сохраняется:

```text
🔎 Могут подойти:

1. @username — <дословный фрагмент анкеты>
```

Имя пользователя остаётся code-owned значением из базы. После тире выводится
только подтверждённый фрагмент анкеты; дополнительный модельный комментарий не
добавляется.

## Границы компонентов

### `prompts/member-matcher.md`

Требует выбрать до пяти участников и вернуть для каждого короткий дословный
`evidence`. Запрещает пересказ и отдельно подчёркивает сохранение чисел, единиц,
субъектов и типа метрики.

### `src/request.matcher.ts`

JSON/Zod schema принимает `{ memberId, evidence }`. Matcher выполняет строгую
проверку принадлежности evidence исходной карточке и возвращает наружу только
проверенный фрагмент.

### `src/requests.ts`

Formatter не генерирует смысловой текст и только HTML-экранирует evidence. Один и
тот же formatter используется публичным `#запрос` и приватным `/test_request`.

## Обработка ошибок

- Неизвестный `memberId`, дубликат или недословный `evidence` отбрасывается.
- Если после проверки результатов меньше требуемого порога, сохраняется текущее
  поведение `no_match`.
- Сбой embedding, PostgreSQL или LLM продолжает обрабатываться существующим путём.
- Тексты запросов, анкеты, evidence и ответы модели не добавляются в логи.

## Тестирование

Регрессионный тест воспроизводит production-дефект: модель предлагает свободный
текст «3,5 млн просмотров», но evidence содержит «более 3,5 млн уникальных
пользователей». Результат обязан содержать только второй, дословный фрагмент.

Дополнительные проверки:

- evidence с изменённым словом, регистром или пробелами отклоняется;
- неизвестные IDs и дубликаты по-прежнему отбрасываются;
- HTML внутри evidence экранируется;
- приватный минимум один и публичный минимум три не меняются;
- публичное исключение автора по Telegram ID не меняется.

## Релиз

Изменение не требует миграции или переиндексации. Перед deploy обязательны
`npm test`, `npm run typecheck`, `npm run build` и `git diff --check`. Релиз идёт
через ветку `codex/private-test-request`; `origin/main` не изменяется без отдельного
разрешения пользователя.

# Приватная тестовая команда подбора участников

**Дата:** 2026-08-30
**Область:** Telegram DM, авторизация владельца, pipeline подбора участников

## 1. Цель

Добавить команду `/test_request <текст>` для ручной проверки реального pipeline
подбора участников в личном чате с ботом. Команда доступна только одному явно
настроенному Telegram user ID и должна возвращать результат уже при одном валидном
совпадении.

Публичный сценарий `#запрос` не меняется: он по-прежнему работает только в forum
topic целевой группы и публикует упоминания лишь при наличии минимум трёх валидных
кандидатов.

## 2. Принятое решение

ID владельца хранится в необязательной deployment-specific переменной
`PRIVATE_TEST_ADMIN_ID`. Сам ID не добавляется в исходный код, Git, документацию
или логи. Семь существующих обязательных production-переменных остаются
обязательными; новая переменная только включает приватную тестовую возможность.

Рассматривались альтернативы:

1. Проверять список администраторов `TARGET_CHAT_ID` через Telegram API. Вариант
   отклонён, потому что он разрешил бы команду всем администраторам, а не одному
   владельцу.
2. Записать ID непосредственно в `runtime-defaults.ts`. Вариант отклонён из-за
   попадания персонального идентификатора в историю Git и привязки сборки к
   конкретному аккаунту.

## 3. Конфигурация и авторизация

- `PRIVATE_TEST_ADMIN_ID` отсутствует или пуст: команда не регистрируется.
- Значение задано: startup валидирует положительный Telegram ID без округления и
  сохраняет его в конфигурации как безопасное целое число.
- Некорректное непустое значение завершает startup понятной конфигурационной
  ошибкой без печати других переменных окружения.
- Handler принимает команду только при `ctx.chat.type === 'private'` и точном
  равенстве `ctx.from.id` настроенному ID.
- В группе, канале и для любого другого пользователя handler не отвечает и не
  раскрывает наличие команды или ожидаемый ID.
- Текст запроса и значение переменной не записываются в логи.

В `.env.example` добавляется только пустое имя переменной. Реальное значение
вносится отдельно в локальный `.env` или Timeweb App Platform и не коммитится.

## 4. Пользовательский поток

Владелец отправляет боту в личном чате:

```text
/test_request Ищу специалиста по B2B-продажам
```

Далее бот:

1. Проверяет private chat и точный Telegram user ID.
2. Если текст после команды пуст, отвечает:
   `Использование: /test_request <текст запроса>`.
3. Для непустого текста отправляет status message
   `⏳ Ищу подходящих участников…`.
4. Проверяет, что выполнен хотя бы один успешный snapshot каталога.
5. Запускает тот же matcher, который обслуживает публичный `#запрос`, но не
   передаёт Telegram ID владельца как исключение. Это позволяет smoke-проверке
   подтвердить собственную карточку владельца; публичный сценарий по-прежнему
   исключает автора.
6. Если валидных совпадений нет, заменяет status message текстом
   `Надёжных совпадений не найдено.`.
7. Если найдено от одного до пяти совпадений, заменяет status message тем же
   HTML-форматом `🔎 Могут подойти:`, который используется публичным сценарием.
8. При внутренней ошибке заменяет status message безопасным текстом
   `Подбор участников временно недоступен. Попробуйте позже.` и пишет только
   разрешённые технические метаданные без запроса, анкет и ответа модели.

Команда не создаёт запись в `member_requests`: эта таблица моделирует
идемпотентную обработку публичных forum messages и требует forum thread ID.
Приватная проверка всё равно использует реальную PostgreSQL-базу через
`MemberRepository.search`, актуальные embeddings и настоящий LLM reranking.
Так тест проверяет каталог и поиск, но не загрязняет production-историю публичных
запросов.

## 5. Изменения компонентов

### Конфигурация

`BotConfig` получает `privateTestAdminId: number | null`. `readConfig` читает
необязательную переменную и использует отдельный parser с fail-fast validation.
Обязательный семипеременный production-контракт не меняется.

### Matcher

`MemberMatcher.match` получает typed options:

```ts
interface MemberMatchOptions {
  requesterTelegramUserId?: string;
  minimumMatches?: 1 | 3;
}
```

Значение `minimumMatches` по умолчанию равно `3`. Оно применяется в двух местах:

- ранний выход после PostgreSQL shortlist;
- финальная проверка числа кандидатов, переживших schema и evidence validation.

Лимит результата остаётся равен пяти. Публичный handler не передаёт override и
сохраняет порог `3`; приватная команда передаёт `minimumMatches: 1`.

### Telegram command

Новый сфокусированный модуль регистрирует `/test_request` и получает matcher,
readiness-check и настроенный admin ID через явные зависимости. `bot.ts` только
подключает этот модуль, когда одновременно доступны request-matching runtime и
`PRIVATE_TEST_ADMIN_ID`.

Форматирование совпадений остаётся code-owned: usernames берутся из проверенных
карточек, а LLM reason проходит существующее HTML escaping. LLM не формирует
Telegram-ссылки и не влияет на авторизацию.

## 6. Границы и ошибки

- Собственная карточка владельца допускается только в приватной smoke-команде.
- При двух активных анкетах команда может вернуть владельца или другого участника.
- Неготовый snapshot, embedding failure, PostgreSQL failure и reranking failure
  дают одинаковое безопасное пользовательское сообщение.
- Неудачный `editMessageText` логируется безопасно; повторное сообщение с
  потенциально дублирующим результатом не отправляется автоматически.
- Команда не меняет consent, active-флаги, embeddings, job state, публикационный
  outbox или данные участников.
- Реализация, release gate и deploy являются отдельными действиями. Эта
  спецификация не разрешает deploy, push или изменение Timeweb-конфигурации.

## 7. Тестирование

Реализация выполняется по TDD. Сначала должны упасть focused tests, затем пройти
после минимального production-кода.

Проверяются:

1. Отсутствующее и корректное значение `PRIVATE_TEST_ADMIN_ID`.
2. Fail-fast для некорректного непустого ID.
3. Команда не отвечает в группе и пользователю с другим ID.
4. Пустая команда владельца возвращает usage и не вызывает matcher.
5. Непустая команда отправляет status message до запуска matcher.
6. Один grounded-кандидат публикуется приватной командой.
7. Приватная команда вызывает matcher без requester exclusion.
8. Нулевой результат редактирует status message без упоминаний.
9. Ошибка readiness/matcher даёт безопасный текст без содержимого запроса.
10. Публичный `#запрос` по-прежнему не публикует один или два результата.
11. Matcher с default options сохраняет порог три, а с `minimumMatches: 1`
    допускает один валидный shortlist/result.

После focused tests выполняется полный release gate:

```bash
npm test
npm run typecheck
npm run build
git diff --check
```

## 8. Критерии готовности

Функция готова локально, когда только настроенный владелец может выполнить
`/test_request` в DM, один валидный кандидат отображается в существующем формате,
собственная карточка допускается только в этом smoke-сценарии, публичные исключение
автора и порог три не изменены, ID и содержимое запроса не попадают в Git или логи,
а полный release gate проходит.
